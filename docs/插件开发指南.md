# Harness 插件开发指南：不依赖创造模式

本指南供 Claude Code、Codex、其他编码 Agent 和人工维护者使用，沉淀 dsh-recap 已验证的 Harness 接入方式。开发所需背景应来自仓库、锁定版本的 SDK 和测试，而不是某个 Agent 的隐藏上下文或专属工具。

**版本基线：DeepSeek Harness 0.2.0-rc.2，Node.js 22.19+。** 依赖声明见 [package.json](../package.json)，实际安装版本由 [package-lock.json](../package-lock.json) 锁定。以下接口是这一基线下的约定，不保证适用于所有未来版本；升级时必须重新核对 SDK、运行实例和集成测试。

## 1. 新 Agent 的最短上手路径

1. 阅读 [AGENTS.md](../AGENTS.md)：产品边界、分层约束和代码质量要求。
2. 阅读 [设计文档](设计文档.md)：当前行为与非目标；不要从旧配置字段推断仍支持某项功能。
3. 阅读 [package.json](../package.json) 与 [构建脚本](../scripts/build.mjs)：确认 SDK 版本、双端入口和构建方式。
4. 按本指南的接口地图查对应实现及测试，再开始修改。
5. 按 [验证说明](验证说明.md) 验证，并区分自动化检查、浏览器组件检查和真实 Harness 验收。

不同编码工具的项目说明入口不同，不保证自动读取 [AGENTS.md](../AGENTS.md)。换用其他 Agent 时，首次任务应明确要求它先阅读该文件与本指南；不需要复制创造模式的提示词，也不需要将整份 SDK 塞进上下文。

在仓库根目录准备依赖及检查基线：

```sh
npm ci --ignore-scripts
npm run typecheck
npm test
```

本仓库使用 npm 和现有锁文件。不要为方便另换包管理器、重建锁文件或升级 SDK。只写文档时无需重新安装已有依赖。

## 2. 没有创造模式，如何确认接口

创造模式的优势主要是按需查询运行实例，而不是自动拥有完整项目知识、历史记忆或更高权限。没有这些工具不妨碍开发，只是需要明确替代证据。

### 离线开发：查锁定 SDK + 仓库测试

安装依赖后，每个 `@deepseek-ai/*` 包通常提供包级 README 和 `lib/types/` 类型声明。优先查公开导出、Context 声明合并、参数类型和返回值，再对照本仓库的实际调用。

| 要确认的内容                  | 本地 SDK 入口（安装依赖后可读）                                                                                                                 |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 投影注册、状态和客户端快照    | [session-projection 类型](../node_modules/@deepseek-ai/dsh-session-projection/lib/types/index.d.ts)                                             |
| 设置、revision、volatile 语义 | [settings 文档](../node_modules/@deepseek-ai/dsh-settings/README.zh.md)、[类型](../node_modules/@deepseek-ai/dsh-settings/lib/types/index.d.ts) |
| 斜杠命令的作用域、记录与取消  | [commands 文档](../node_modules/@deepseek-ai/dsh-commands/README.zh.md)                                                                         |
| Slot 类型、注册与生命周期     | [slots 文档](../node_modules/@deepseek-ai/dsh-client-ui-slots/README.zh.md)及所接入 UI 包的 `/client` 类型                                      |
| 模型流、路由与消息类型        | `@deepseek-ai/dsh-llm` 的公开导出和类型                                                                                                         |
| 认证请求的注册与传输          | `@deepseek-ai/dsh-client-connection` 的公开导出和类型                                                                                           |

这些 SDK 链接不是仓库自带文件，未安装依赖或在源码网站上查看时可能不可打开。SDK README 内的源码仓库相对链接也可能不随 npm 包发布；不要将链接失效理解为接口不存在。

TypeScript 中 `import type {} from '某个 Harness 包'` 可用于加载该包的类型扩展，不是多余代码。移除前应确认是否会使 `Context`、事件或 Slot 类型丢失。不要用 `any`、随意强转或自造接口掩盖版本不匹配。

### 有运行时自检工具：用它补充现场证据

若当前 Agent 提供 `cordis_inspect_list` / `cordis_inspect_query`：

1. 先列出 Provider，使用返回的准确 platform、provider、method 和输入 schema；不要猜名字。
2. 按需查询 Service、Event、Config、Tool，以及 Client 的 Slot、Builtin、Theme。
3. 查询结果用于确认真实接口、事件模式和扩展点，不是插件可以调用的业务 Service。
4. Inspect 是只读检查，不负责安装、保存设置或执行业务操作。Client 查询需要已连接的 Harness 页面。

不要假定 `cordis_define` / `cordis_run` 等工具一定存在，也不要把某次会话的工具清单当成固定 SDK。查到运行接口与工作区 SDK 不一致时，先核对版本和运行实例；不能只让类型检查“通过”。

需要源码时使用明确定位、版本匹配的 Harness checkout。桌面安装可能采用 `app.asar`，普通 shell 搜索不一定能将其视作目录；优先使用工作区 SDK，不把安装包路径写进仓库，也不为开发插件直接修改已安装应用。

## 4. Host：服务接入与后台任务

### 分层、注入和清理

- core 保持无 Harness 依赖，通过 [EnginePorts](../src/core/contracts.ts) 接收配置、事实快照、生成函数等端口。
- Host 负责真实服务适配。当前必需依赖为 `agents`、`sessionProjections`；可选命令、Connection 等能力通过 `ctx.inject([...], child => ...)` 接入，不能假定所有 profile 都有。
- 可选能力的读取使用 `ctx.get(...)` 并处理缺失。SDK 类型存在不等于运行实例已加载该服务。
- 注册、计时器、订阅和任务必须随所属插件生命周期清理。自建资源通过 `ctx.effect` 返回 disposer，参考 [Host 入口](../src/host/index.ts)；不要创建卸载后仍运行的全局任务。
- 全局插件与 Agent preset 是不同作用域。命令在 Agent 上下文下注册时具有 Agent 作用域；不要把会话局部状态放进全局共享对象而不加会话边界。

### 投影，而不是每次扫描完整日志

本项目用 `dshRecapFacts` 注册 Host-only 投影，扩展 `SessionProjectionStateMap`。框架驱动 `init / apply`，业务从 `stateOf(agent.session, key)` 读取；目标、待办和标题从原生投影快照获取。

关键约定：

- `init / apply` 必须同步、纯逻辑；状态必须可 JSON 序列化，不放 Agent、函数、Promise 或控制器。
- 无关事件返回原 state 引用；不要原地修改框架返回的 live state。
- 状态有容量边界；改变序列化结构或 fold 语义时更新 `stateVersion`，避免误用旧检查点。
- 未注册的可选域按缺失处理，不伪造事实。但投影单元表是进程级的，不能用 key 是否存在判断某个会话是否启用了该功能；逐会话判断必须读取实际值。框架可能在首次读取时重放历史，这不等于允许业务每次遍历全日志。
- Host-only 只表示不发布 Client wire view，**不表示没有持久化检查点**。Recap 摘要内存缓存与 Harness 原生投影持久化是两回事。

实现与压缩事务处理见 [投影](../src/core/projection.ts)，读取见 [适配器](../src/host/adapter.ts)，回归见 [core 测试](../tests/core.test.ts)。不要为回顾自造未知 session event type。

`session/event` 在当前版本是提交后的 `emit` 通知，签名为 `(session, event)`，不是可否决提交的拦截器。事件监听中只做轻量状态更新，不同步等待摘要生成。它与 `agent/pre-step` 的 middleware / waterfall 用法不同，修改 hook 前必须确认模式。

### 命令即时受理，生成在后台

`commands.register` 的名称不包含 `/`；处理器自行解析 `rawInput`，返回原生 `CommandResult`。当前 `/recap` 在调度受理后立即返回，不等待模型流结束。

- “已受理”与“已生成完成”必须分开表达。
- 成功返回后由 Harness 处理已提交输入的清空；插件不操作输入框，尤其不能清除生成期间的新草稿。
- 后台 Promise 必须处理错误并纳入插件清理，不能只是丢弃一个不受管理的异步调用。
- 命令输入和结果不自动进入模型上下文，但原生命令生命周期会写会话日志。不要将“不会注入模型”写成“完全不落盘”。

参考 [命令适配](../src/host/commands.ts) 与 [慢模型、命令及卸载集成测试](../tests/host.integration.test.ts)。

### 模型与取消

使用 Harness 已有 LLM 服务，不另建持有 API Key 的第三方客户端。本项目的路由顺序是显式 provider + model、会话最近请求配置、Agent 配置；不能只复制模型名而丢掉 provider。

通过 `llm.stream` 传入独立请求、输出预算、`signal` 和 `sessionId`，用 `BlockAssembler` 拼流。当前实现只把正常 `stop` 视为完整成功，超时、失败、不完整流保留旧摘要并显示失败原因，不用原始消息降级。不启用工具，不执行摘要中的操作。当前 SDK 的 `purpose` 有限定用途，Recap 省略它，不冒用其他功能的标识。

**取消与失效校验必须同时存在：** 控制器终止请求后，仍要核对 epoch、任务身份、配置签名、Agent 实例、事实水位、语言及可见性，才能提交结果。否则不遵循信号的服务商或迟到响应仍可能覆盖新状态。

参考 [调度器](../src/core/engine.ts)、[异步工具](../src/core/async.ts) 与 [取消和过期结果测试](../tests/engine.test.ts)。取消本地等待不保证远程模型已停止执行或停止计费。

## 5. Client：宿主模块，不是独立 React 应用

### ModuleLoader 与外置依赖

[构建脚本](../scripts/build.mjs) 把 Client 编译为 CJS，再包装进 `window.__ModuleLoader__.load({ id, factory(require) })`；React 由宿主 `require` 提供，不打进插件包。

- Client 源码导出 `inject` 和 `apply(ctx)`，不是自行 `createRoot` 启动另一个应用。
- React 虽在开发依赖中，也必须 external。Harness UI 类型通过 type-only import 引入，不把 UI 包源码打入浏览器产物。
- 添加运行时 import 前核对宿主可提供的模块与 bundle 结果；typecheck 通过不代表浏览器一定能加载该模块。
- [package.json](../package.json) 的包名、Client export、`dsh.client.inject`，以及 ModuleLoader ID、[bundle patch](../cordis.patch.yml) 的插件名必须协调一致。改包名或 scope 不能只改一处。
- `dsh.client.inject` 描述模块依赖，源码 `inject = ['slots', 'locale', 'remote', 'remote.session']` 描述 Cordis 服务依赖，两者不是同一清单。

[包检查脚本](../scripts/check-package.mjs) 会验证 ModuleLoader 工厂、宿主 React、无 Harness 运行时 require 和 Host 导出。更换构建方案不能绕过这些检查。

### Slot、props 和 UI 生命周期

当前注册位置（另有 `conversation.input.dock`，仅补充空白会话的命令反馈；普通会话返回空）：

| Slot                            | 注册标识                            | 用途                   |
| ------------------------------- | ----------------------------------- | ---------------------- |
| `conversation.chat.commandview` | `key: 'recap'`                      | 手动摘要与命令提示     |
| `conversation.chat.turnTail`    | `id: 'dsh-recap'`、`order`          | 最新完成轮次的回顾文字 |
| `settings.section`              | `id: 'dsh-recap'`、`order`、`label` | 原生设置页             |

先 `ctx.slots.inject(slotName, ...)`，在可用的声明下注册；不要注册猜测的 Slot，也不要为加一段文字替换整个聊天界面。区分 `single / list / keyed / chain`，替换已有席位可能遮蔽官方 UI。

模型选择复用 `ctx.remote.session.modelCatalog()` 的官方目录，必须声明 `remote` 和 `remote.session` 服务依赖；只导入类型不能授予运行时访问。Client 模块依赖包含 `@deepseek-ai/dsh-api-gateway`。回顾设置只保存自身的 provider/model 覆盖，不调用会改变主会话模型的 `selectModel()`。

组件使用宿主推导的 `CommandRowProps`、`TurnTailOwnerProps` 等类型，通过 `useChat / useSession` 判断当前会话、最新轮次和加载状态；不扫描 DOM 或完整日志计算 UI 数据。

样式节点由 `ctx.effect` 清理；展示请求、轮询和事件监听在 React effect cleanup 中撤销；用户设置保存队列独立于面板，关窗后继续有限的已授权保存。语言切换通过 locale 订阅和动态 label 更新，不通过重新注册设置页丢掉草稿。参考 [Client 入口](../src/client/index.tsx)、[请求生命周期](../src/client/use-recap.ts) 与 [Client 注册测试](../tests/client-entry.test.ts)。

## 6. HTTP 与设置：保留认证和冲突保护

### HTTP

Host 通过 `ctx.connection.fetch.register({ path, methods, requestBody, fetch })` 注册插件 API，利用 Harness 的认证、Host / Origin 校验。Client 优先使用 `globalThis.__DSH_TRANSPORT__.fetch`，以适配宿主传输；不能为方便测试将接口改成公开 WebServer 路由。

当前 API 使用严格输入校验、JSON content-type、实际流式字节上限、统一错误返回，以及 Client 超时和调用者信号合并。不要向浏览器暴露内部异常、凭据或原始会话素材。对未加载或未知会话返回不可用，不为摘要请求自行激活冷会话。

参考 [HTTP 适配](../src/host/http.ts)、[Client API](../src/client/api.ts) 与 [真实认证测试](../tests/auth.integration.test.ts)。

### 设置

当前设置由 Schemastery Config 的 `.volatile()` 声明，业务通过 `config.get()` 读取，由原生 Settings 持久化到 profile patch，不另存一份权威 JSON 配置。

保存流程必须保留：

1. 通过当前 `ctx.fiber` 在 `configEditor.entries()` 找所属 entry，再对应 `settings.describe()` 的 namespace；**namespace 是 profile entry id，不一定等于包名**。
2. 读取当前配置与 revision，只提交修改字段和读取时的 revision。
3. 校验 patch 及合并后的完整配置，调用 `settings.update(ns, patch, expectedRevision)`；仅在调用前检查一次 revision 不足以防止并发覆盖。
4. 冲突返回 409，保留用户草稿，让用户显式重新读取；缺少可写 Settings 时降级为只读，而不是直接修改 profile 文件。

参考 [设置桥接](../src/host/settings.ts)、[设置 UI](../src/client/Settings.tsx) 与 [隔离配置、改名 entry 和并发测试](../tests/settings.integration.test.ts)。

字段的唯一来源是 [core Config](../src/core/config.ts) 的 `FIELDS`。新增字段应同步验证、表单和测试，并运行 `npm run docs:config` 更新 [自动生成的配置说明](配置说明.md)，不要手工维护第二份字段表。若将来增加 secret 字段，对外描述必须脱敏，不能用不完整的脱敏值整体替换配置。

## 7. 构建、安装与真实页面更新

### 可复现构建

```sh
npm run check
npm run format:check
npm run test:browser
npm pack
```

`check` 包含严格类型检查、测试、双端构建与包入口检查。构建脚本会重建仓库根目录下的 `dist`，不要在里面保存手写文件。浏览器测试使用独立组件页面和合成数据，不读取生产凭据、不调用付费模型；按 [验证说明](验证说明.md) 配置 Chrome / Playwright。

### 安装不以创造模式为前提

源码开发、测试和打包只需要普通文件与命令工具。加载到真实 Harness 是独立步骤：

- 用**目标运行实例**当前版本支持的插件管理入口安装已构建的目录或打包文件，不手改用户 profile 或 Harness 源码。
- 若 Agent 有 `plugin_manager`，先列出插件获取准确标识，再申请相应安装、启停或替换操作；它不是只读 Inspect。
- 若 Agent 没有插件管理工具，由维护者通过该版本支持的 UI / CLI 完成加载。CLI 不在 PATH 不代表桌面 Harness 未运行；先查实际启动方式和当前 CLI 帮助，不照搬旧版命令或另起一套实例。
- 安装入口支持哪些本地路径或安装规格必须以当前版本确认；本指南不假定所有 UI 都接受目录或 tarball。
- 已有插件占用 `/recap` 时先处理旧插件，避免同一作用域的同名注册冲突。不要未经确认卸载或删除用户配置。
- SDK / Harness 版本不兼容时优先对齐版本，不默认授予版本豁免。安装、启停与重启均可能影响同一 profile 的其他会话，必须获得用户授权。

### 构建通过不等于当前页面已更新

| 修改范围                     | 必须确认的更新步骤                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------- |
| 本仓库源码                   | 构建、确认运行实例使用的是最新安装产物，再按加载方式更新插件                             |
| Host 插件                    | 确认已重新加载 Host；若是 startup profile，则需要重启                                    |
| Client 插件                  | 确认新 bundle 已生成且被目标实例加载；无可靠 HMR 时刷新原 Harness 页面                   |
| Harness 官方 Client 插件源码 | 只有同一 checkout 的 `pnpm run dev:web` 构建 watcher 正在运行时，才可依赖对应 Client HMR |
| Harness Web shell / 普通包   | 重建受影响 Web 产物，并在原运行实例页面刷新验证，不能只依赖插件 HMR                      |

不能因源码已保存、组件测试通过或 HMR 接收端存在，就承诺当前 GUI 自动更新。不要另起一个开发服务器冒充正在使用的 Harness；Web shell 还依赖 `dsh web` 注入启动信息，并非单独 Vite 页面即可等价运行。真实验收前记录目标实例、版本、profile、页面 URL 和插件来源，但不要将本机路径或认证信息提交到仓库。

若 `/recap` 已受理但没有显示，先检查认证状态接口 `/api/dsh-recap/state`：`status: ready` 且有 `recap.text` 表示摘要已生成；当前 Client 还要求 `hidden: false` 且 `displayTurn` 等于展示轮次。若响应缺少 `displayTurn`，而当前源码已定义该字段，应检查是否为旧 Host 进程搭配新 Client 产物。插件停用后重新启用可能仍复用进程中的模块缓存，不能据此认定已加载新代码；需要重启目标 Harness 进程、刷新页面，再验证命令与实际展示。不要通过放宽轮次校验掩盖版本不一致。

## 8. 验证与交付清单

- [ ] API 已按目标版本 SDK / 运行实例核对，没有凭记忆猜接口。
- [ ] core 无 Harness 依赖，Host / Client 各自接入对应服务。
- [ ] 新行为有测试；取消、过期结果、卸载清理、缺失能力和错误降级不被破坏。
- [ ] 设置保留 revision 冲突保护；HTTP 保留认证边界。
- [ ] Client 使用 ModuleLoader，未打包第二份 React / Harness UI。
- [ ] 默认模型上下文保持不变；可选注入仍使用合法消息与明确开关。
- [ ] 修改文件已执行 Prettier；typecheck、相关测试和构建检查通过。
- [ ] UI / 加载变更区分组件测试与真实 Harness 验收，不把未做的验收写成已完成。
- [ ] 没有生产凭据、私人会话、本机路径、coverage、截图或临时构建文件进入提交。
- [ ] 升级 SDK 或改变接入约定时，同步更新本指南、对应测试和版本说明。

仅文档修改可缩小验证范围；业务或接入变更按 [验证说明](验证说明.md) 执行完整检查。涉及真实模型时先征得用户同意并说明额度影响，优先合成数据和隔离 profile。

常见排查顺序：类型缺失先查依赖版本与类型扩展；组件不出现先查 Slot 声明、Client 依赖及实际 bundle；页面仍旧先查安装来源和重载；401 / 403 先查宿主传输与认证来源；设置只读查 entry 和 Settings 能力，409 查 revision；命令冲突查旧插件与作用域。不要以移除保护、强制类型转换或开启全部权限作为默认修复。
